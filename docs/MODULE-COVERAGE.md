## Ordering hazards

Planned files that a later slice structurally depends on, where the
backlog's stated sequence does not make the dependency visible:

1. **S7 -> `comboreduct/interpreter/eval.cc`.** `general_rules.cc` (named
   explicitly in S7) calls `eval_binding`/`eval_throws_tree` to evaluate
   subexpressions during reduction. S7's backlog line lists `reduct.py,
   meta_rules, general_rules, flat_normal_form, logical_rules,
   logical_reduction` and stops there -- `eval.py` has to land no later
   than `general_rules.py`, but nothing in the backlog says so.
2. **S8 -> `comboreduct/type_checker/type_tree.h`.** `build_knobs`'s
   constructor signature is `build_knobs(combo_tree&, const type_tree&,
   representation&, ...)`, and `build_knobs.cc` calls
   `get_signature_output`/`type_tree_arity`/`boolean_arity`/
   `type_tree_sib_it` throughout. S8's backlog line names 8 modules in
   `representation/` and none in `type_checker/` -- yet the S0-S6
   foundation cycle explicitly scoped `type_checker/` out entirely
   (table.py's own docstring calls this out), so S8 silently reopens a
   gap the previous cycle closed the door on.
3. **S10 -> `moses/moses/metapopulation/ensemble.h`.**
   `metapopulation.h:45` unconditionally `#include`s `ensemble.h`. S10's
   backlog line ("`metapopulation/` + `merging.py`") never mentions
   ensembles, which are explicitly P2 ("ensembles/boosting"). A literal,
   header-for-header port of `metapopulation.h` at S10 cannot compile
   (conceptually) without at least a stub `ensemble` type.
4. **S11 -> the other three optimizers + `ss_bscore.h`.**
   `moses_main.h` (S11) `#include`s `star-anneal.h`, `univariate.h`,
   `particle-swarm.h`, and `scoring/ss_bscore.h` -- all four PLANNED: P2.
   Softer than the other three hazards: classic dispatches between
   optimizers via a CLI flag, so a minimal S11 port can wire hill-climbing
   only and defer the rest, but that decision needs to be made explicitly
   rather than falling out of a literal per-file port.
