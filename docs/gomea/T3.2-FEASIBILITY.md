# T3.2 feasibility note: real-valued GOMEA on the constants (2026-11-23)

**Status:** agent-written, at the user's request (2026-11-23: "let's go straight to the real-valued
GOMEA please", `APPROVALS.md`). The roadmap rule says that each tier 2 task starts with a feasibility
note, and that the user decides on the note before any design (`ROADMAP.md`, stage 3). Nothing is
designed or built.

**Origin:** the method is from a paper: Koch, Alderliesten and Bosman, "Simultaneous Model-Based
Evolution of Constants and Expression Structure in GP-GOMEA for Symbolic Regression", PPSN 2024
(DOI 10.1007/978-3-031-70055-2_15; preprint arXiv 2606.02236, which its own page calls the "PPSN 2024
Preprint"), found in the literature search of 2026-11-06 (`LITERATURE-2026-11-06.md`, category B,
item 1; `BACKLOG.md` section 8, B1). It builds on RV-GOMEA (Bouter et al., GECCO 2017). The way to put
it into MOSES (option C below, the rules, the arms) is agent-designed. The support from our rounds is
post hoc. Not approved as a setting.

## The idea

pyMOSES GOMEA never makes a new constant inside a deme. Real-valued GOMEA estimates a Gaussian
distribution of the good constant values in the population, samples new values from it, and keeps
a new value when the program is not worse (optimal mixing with sampling). So the population shares
what it learns about the constants, as GOM shares structure.

**What the paper did (read from the preprint, 2026-11-23):**

* GP-GOMEA evolves the structure (a tree template, height 5); each genotype also has a pool of 10
  real constants that the tree can use as terminals.
* Each generation interleaves GP steps (GOM on one FOS subset) with full RV-GOMEA generations on the
  constant pools. A rule keeps the RV evaluations near half of the GP evaluations: an RV step runs
  with probability p_RV = 1 − 0.5 · (RV evaluations / GP evaluations).
* The Gaussian model uses the best 35 % of the values; AMS and AVS as in RV-GOMEA. Constants start
  uniform in [min y, max y] of the training target.
* **Intron-aware (IA):** a change to a constant that the tree does not use is not evaluated, and only
  the used values enter the Gaussian model.
* Setup: population 1,000, 10^7 evaluations, 5 real datasets (Airfoil, Concrete, Energy cooling and
  heating, Yacht: 5 of our 10), 35 runs each.

**Measured result on real data, with linear scaling and restarts** (Table 4; a Bayesian correlated
t-test, "equal" means within 0.01 R²):

| Comparison | P(better) | P(equal) | P(worse) |
|---|---|---|---|
| RV against fixed constants (ERCs) | 0.581 | 0.400 | 0.019 |
| RV + IA against fixed constants | 0.771 | 0.205 | 0.025 |
| RV + IA against fixed constants + coefficient mutation | 0.918 | 0.026 | 0.056 |
| RV + IA against RV | 0.020 | 0.971 | 0.009 |

* The paper says the RV methods "also lead to larger expressions" on real data, and that "a
  multi-objective approach is needed". It gives no run time, and it was not compared with LM or
  another gradient method during the search.
* (Correction of the agent's message of 2026-11-23: the value 0.77 is for the intron-aware variant;
  plain RV gives 0.58 with 0.40 equal.)

## What our data say about constants in MOSES

**In MOSES regression, the genome is the constants.** In all 485 demes of BASE-TLS and TLS-NP in
round 14 (38,533 genes), 100 % of the genes are constant genes (agent measurement on the round 14
`events.jsonl`). The continuous knob building puts a coefficient on every term of nested linear
combinations; a coefficient of 0 removes its term. So the structure of a program is which
coefficients are not zero, and the values are the coefficients.

**A constant gene today** (`pymoses/gomea/schema.py`, `contin_value`, `sample_contin_code`):

* It is a MOSES contin knob of depth 5: a path of up to 5 left or right steps from the exemplar's
  value. The step size grows while the path keeps one direction and halves after a turn
  (`field_set.contin_stepper`). So it has 63 possible values, on a grid, within about ±31 step
  sizes of its start.
* GOMEA only copies these codes between individuals (`--gomea-contin copy`). Inside a deme, no new
  value appears. The next deme builds a new grid around the new exemplar.
* The schema can already hold any real value in a gene ("free codes", `register_contin_value`,
  added for `--const-opt mutate`). A free value packs to code 0 in the MOSES instance.

**Our earlier constant work:**

| Round | Method | Result |
|---|---|---|
| 3 (1an) | LM, Gaussian coefficient mutation after each GOM step (`mutate`), polish | all ties; the rule chose LM |
| 5–7 (1at, 1aw) | LM with a validation guard (LM-VAL) | qualified; dropped when BASE-TLS (no LM) won |
| 12 (1bf) | LM during the search (BASE-LME) | tie, 0.929, programs 1.27× |
| 13 (1bh) | LM inside the terms (T3.1) | tie, 1.000 (LM had little budget) |
| 14 (1bi) | LM inside the terms with a budget (TLS-LMR) | tie, 0.980 (63/23) |

All of these tune one program at a time. Real-valued GOMEA is different: it learns the
distribution of good values across the population. The per-term least squares of BASE-TLS already
fits the outer weight of each term exactly, so the remaining work is on the constants inside the
terms.

## The key difference from the paper

The paper has separate structure genes (discrete) and a small pool of 10 constants (real). In MOSES
there is one kind of gene, and it carries both: zero or not zero (structure) and its value. A plain
real-valued model on these genes would almost never sample exactly 0, so terms could no longer be
switched off. Three ways out:

| Option | What changes | For | Against |
|---|---|---|---|
| **A. Split each gene** into an on/off bit (discrete, GOM and linkage as now) and a real value (RV-GOMEA, used only when on) | the genome and the schema | the paper's model exactly (structure discrete, constants real) | doubles the genome; a new genotype type; the most code |
| B. Real values only (0 is just a value) | the schema | simple | terms cannot switch off; loses MOSES's structure search |
| **C. Keep the codes, add RV steps (agent recommendation)** | an opt-in RV step between GOM steps that samples new real values for the **non-zero** genes and stores them as free codes | GOM, linkage and the structure stay as now; free codes already exist; intron-aware by construction (zero genes are never sampled) | values move only in RV steps; one more step type to balance |

With option C, a gene can still become 0 or leave 0 through GOM (a code path), and RV steps refine
the values of the terms that exist.

## How it fits into BASE-TLS (option C)

| Part | Today (BASE-TLS) | With RV steps |
|---|---|---|
| Outer loop (metapopulation, exemplar, demes) | `deme_expander`, `metapopulation` | Unchanged |
| Representation building | `build_knobs`, contin knobs of depth 5 | Unchanged |
| GOM on the codes, linkage (LT-B) | `pymoses/gomea/engine.py`, `fos.py` | Unchanged |
| New values inside a deme | none | **New:** an RV step: for each FOS subset of the real model, a Gaussian from the best 35 % of the population's non-zero values of those genes; sample, evaluate, keep if not worse; store as free codes |
| Balance between GOM and RV | – | **New:** the paper's rule p_RV = 1 − 0.5 · (RV evaluations / GOM evaluations) |
| The FOS of the real-valued part | – | **New:** univariate, or small blocks from the node-proximity grouping (the knobs of one term), because a full Gaussian over 44–223 genes cannot be estimated from a population of about 100 |
| Scorer | `--linear-scaling terms` | Unchanged |
| Budget | every evaluation counts | Unchanged: every RV sample is a full evaluation and counts |
| Runner, report | unchanged | Unchanged, plus RV counters in the telemetry |

## What is new (code)

| Part | Where (proposed) | Content |
|---|---|---|
| RV step | `pymoses/gomea/` (a new module, called from the engine loop) | estimation (mean, variance or block covariance), sampling, accept if not worse, optional AMS and AVS |
| Active and inert genes | same module | sample only non-zero genes; skip a gene whose value the per-term fit absorbs (the multiplier of a whole top-level term), as the LM inert-column rule does |
| Real values in genotypes | `schema.py` | reuse the free codes; the table grows by at most the deme's evaluations (20,000 per run in the rounds) |
| Engine hook | `engine.py` | an opt-in step between GOM steps, with the balance rule; with the option off, every output stays byte-identical |
| CLI | `problem_params.py` | for example `--gomea-contin rv` or `--gomea-rv-step on`, with the FOS choice of the real part; refusals where it does not apply (`--gomea-contin reject`, HC) |
| Telemetry | engine records | RV evaluations, accepted RV samples, share of evaluations, inert skips |

## What it can break, and the risks

* **The port rule.** The option is opt-in, and identity tests prove that every existing output stays
  byte-identical without it.
* **Cost.** Every RV sample is a full evaluation of the program on all training rows (no partial
  evaluation, unlike RV-GOMEA's own benchmarks). At an equal budget, RV steps take evaluations from
  GOM. The balance rule gives them about a third of all evaluations.
* **Size.** The paper found larger expressions on real data with RV. This goes against the user's
  preference for smaller programs; PEN125 stays on, and size is a registered contrast.
* **Overfitting.** RV fits the constants harder to the training rows. Our LM history showed this (the
  validation guard of round 5 cut the WiR gap from 9.69 to 4.04). A validation guard for RV, or the
  report's train–test gap, is needed.
* **Wasted samples on inert genes.** Under per-term least squares, a constant that only scales a whole
  term changes nothing. Without the inert rule these samples cost evaluations for nothing. The spike
  measures how many genes are inert.
* **Population size.** RV-GOMEA's guideline is a population of at least 17 + 3·λ^1.5 for a FOS subset
  of λ genes (Bouter et al. 2017): about 20 for univariate, about 41 for blocks of 4. The dynamic
  population of BASE-TLS has about 100 per deme, so only small subsets are possible.
* **Short demes.** BASE-TLS has about 2 demes of a few generations each. A Gaussian model needs some
  generations to move; the spike checks how many RV steps a deme gets.

## What to expect

* **From the paper:** a moderate gain with linear scaling, P(better) 0.58 (plain) to 0.77 (IA), most
  of the rest "equal within 0.01 R²", on 5 of our datasets, at 10^7 evaluations (we use 20,000).
* **From our rounds:** every constant method so far tied with the reference, with gains of 0–7 %.
  Per-term least squares already does the largest part of the coefficient work.
* **Agent reading:** a gain is most likely where BASE-TLS programs have constants inside their
  terms that matter (for example ratio programs on Yac, where LM closed most of the gap in round 14);
  little gain where the programs are near-linear (Dow). The budget of 20,000 evaluations is 500 times
  smaller than the paper's, which limits how far a Gaussian model can move.

## How to build it (proposed order)

1. **The user decides on this note.**
2. **A code spike** (one subagent, about half a day, no commit to the branch): can an RV step run
   inside the engine loop with free codes; how many genes are non-zero and how many are inert in
   BASE-TLS demes; how many RV steps a 20,000-evaluation run gets.
3. **Design note and code pre-registration** (agent; the user approves): option, FOS of the real
   part, balance rule, inert rule, guard, telemetry, identity tests.
4. **Clone** (subagent): the code and tests; a local pilot on Con and Dow.
5. Merge, full suite, RV16 review, push with approval, then a server round. Candidate arms (agent
   proposal): BASE-TLS (reference), BASE-TLS-RV (option C), TLS-LMR (LM inside the terms, the best
   constant method so far), TLS-NP; fresh splits; test NMSE, size and CPU registered.

## Effort

* Option C: about 400–700 lines under `pymoses` and 500–800 lines of tests; one subagent clone plus
  the spike; about 2–4 working days locally with the full suite and the RV16 review; one server round
  of about 10–15 h.
* Option A: about twice that, because the genotype type changes.
