## The idea

An IT (interaction–transformation) model has a fixed shape:

prediction = w0 + w1·g1(m1) + w2·g2(m2) + … + wk·gk(mk)

* Each **interaction** m is a product of inputs with small integer powers, for example x1·x3 or
  x2²·x5⁻¹.
* Each **transformation** g is one function of the interaction (identity, or sin, exp, log).
* The **weights** w come from least squares, as in BASE-TLS today.

In MOSES this is a third representation-building path, beside the boolean and the continuous
paths. Its knobs come from a fixed template, not from the shape of the exemplar. So every deme has
the same knob vector, with the same length and the same meaning at each position.

**How much of today's search result it can write.** 85 of the 100 BASE-TLS programs are
polynomials. Multiplied out, they have a median of 13–43 monomials per dataset (Tow 43, Dow 27,
the others 13–19). The highest power of one input is 4 (Air), the highest degree 5. With free
weights for each monomial, an IT model with enough terms contains each of these 85 programs. The
other 15 are ratios: all 10 Yac programs and 5 of 10 Bos programs. The IT form cannot write a
ratio of two sums. The rational form TIR (de França, GECCO 2022, arXiv 2205.06807) can; it is a
later step.

## How it fits into BASE-TLS

BASE-TLS is GOMEA with LT-B linkage, the dynamic population, PEN125 and per-term least squares,
with no LM. The IT path changes only the representation-building step and the decoding of a knob
vector into a program. Everything else stays:

| Part | Today (BASE-TLS) | With the IT path |
|---|---|---|
| Outer loop (metapopulation, exemplar, demes) | `deme_expander`, `metapopulation` | Unchanged. A new deme restarts GOMEA from the exemplar's knob vector |
| Representation building | `build_knobs` (continuous path), knobs from the exemplar's shape | **New:** knobs from the fixed IT template |
| Knob vector → program | `FrozenSchema.candidate` walks the exemplar tree (`pymoses/gomea/schema.py`) | **New:** an IT schema writes the IT tree directly |
| Deme optimizer | GOMEA, LT-B, dynamic population | Unchanged (LT-B learns from any discrete vector) |
| Acceptance | PEN125 on the tree's complexity | Unchanged |
| Scorer | `--linear-scaling terms`, `bscores.fit_program_terms` | Unchanged, plus one opt-in rule for repeated or aliased term columns (see "What is new") |
| Constants | Contin knobs inside the terms; no LM | **None inside the terms:** the weights do the work; `--const-opt none` |
| Runner and report | trees, size = nodes + terms | Unchanged: the IT tree prints as a normal MOSES program |

A run of the new arm would be the BASE-TLS command plus the IT options, for example
`--representation it --it-terms 64 --it-factors 3 --it-powers=-2,-1,1,2` (names to be decided in
the design).

## Two ways to encode a term

| Encoding | Knobs of one term slot | Dow (57 inputs), 64 slots | For | Against |
|---|---|---|---|---|
| **Dense:** one power for each input | 57 knobs (power −2…2) | 3,648 knobs | The ITEA genome; simple | Huge on Dow and Tow; a random start makes dense terms |
| **Sparse (agent recommendation):** f factor slots, each = (input or none, power) | 2f knobs (f = 3: 6) | 384 knobs | Small on every dataset; a term is a product of at most f factors; "none" everywhere = the slot is off | A new encoding, not the paper's |

* With the sparse form, a repeated input gives higher powers (x1²·x1² = x1⁴, as Air needs).
* The default value of each knob is "none", so the empty model is the start exemplar, as MOSES
  starts today. The GOMEA start population samples near the exemplar (radii 1–4 and some wide
  samples), so the first models are sparse.
* For reference: BASE-TLS had a median of 74 knobs per deme (Dow 118); TLS-LMR had 195.5 (Dow
  1,742).

## What is new (code)

| Part | Where (proposed) | Content |
|---|---|---|
| IT template | new module under `pymoses/moses/representation/` | slots, factor slots, power set; the rule "negative powers only for inputs with no zero in the training rows" |
| Decoder | same module | knob vector → canonical IT tree (terms and factors sorted; equal monomials merged; for a 0/1 input, x² = x); no MOSES reduction, so the IT form stays |
| Encoder | same module | IT tree → knob vector, for the exemplar of a new deme (a per-run table from the printed tree to its vector) |
| IT schema for GOMEA | `pymoses/gomea/` beside `schema.py` | the interface that the engine uses from `FrozenSchema` (default vector, domains, decode, candidate, phenotype key, schema id) |
| Hook | `deme_expander` (where the representation is built) and the CLI (`problem_params.py`) | `--representation it` picks the IT path; refusals for options that do not apply (HC, LM, `--gomea-contin`) |
| Scorer rule (opt-in, IT only) | `bscores` / `least_squares` | drop a term column that repeats or aliases another, as `sr_linear.py` does for OLS; today one aliased column makes the whole per-term fit fall back to plain `a + b·f` |
| NP linkage (later) | `node_proximity.py` | the knobs of one slot are "near"; LT-B needs nothing |

## What it can break, and the risks

* **The port rule.** The path is opt-in. Without `--representation it`, every output stays
  byte-identical (identity tests on the existing manifests and the C++ golden fixtures).
* **The GOMEA engine assumes a tree-walk schema.** `FrozenSchema` reads the exemplar tree and the
  knob locations (`rep._exemplar`, `find_disc_knob`, `find_contin_knob`). The IT schema must give
  the engine the same interface without them. This is the largest unknown; a short code spike
  answers it first.
* **Reduction.** MOSES reduction could reorder or factor an IT tree (for example
  `x1·x2 + x1·x3` → `x1·(x2 + x3)`), and then the encoder cannot read it back. So the IT path
  skips the reduction and dedupes by its own canonical form.
* **Invalid terms.** x⁻¹ with x = 0, or a log of a negative value, gives non-finite columns, and
  then the per-term fit falls back for the whole model. The template rule above avoids division by
  zero on the training rows; it cannot guarantee the test rows (the clipped NMSE stays in the
  report).
* **Model size.** IT models need more terms than a nested tree for the same polynomial (Tow: 43
  monomials against 21.5 terms). PEN125 limits growth, but IT programs can be larger.
* **Yac and half of Bos** use ratios, which IT cannot write. Expect a loss there unless TIR is
  added.

## What to expect

* **Agent reading of the round 13 and 14 data (post hoc):** a gain is most likely on Dow (the linear
  model is in the IT space, and 64 slots can use all 57 inputs); about the same on the datasets
  where BASE-TLS finds polynomials of degree 2–3 (Air, Con, EnC, EnH, Tow, WiR, WiW); a loss on Yac.
* **Published evidence (caution):** in the SRBench black-box track, ITEA has a median test R² of
  0.713 (rank 11 of 21) and a median size of 111, against GP-GOMEA 0.816 and 25.5 (recomputed from
  the SRBench results file in our research notes, `reports/Building blocks for symbolic
  regression.md`). SRBench also states that methods with a fixed model shape (ITEA, FEAT, FFX, BSR)
  find the true formula less often. So the IT form alone is not known to beat tree GP. The reasons
  to try it here are specific to MOSES with GOMEA: a fixed-length discrete vector suits GOMEA's
  linkage, and the per-term fit always acts.
